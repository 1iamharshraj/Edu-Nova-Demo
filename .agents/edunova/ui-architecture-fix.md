# UI Architecture Fix — Entity Pickers & Modal-as-Page

Triggered by a live UX audit: (1) ~20+ places pick a student/teacher/staff member from a flat `<select>` populated with the ENTIRE school roster (`db.users.filter(role===...)`) — unusable at real school scale, confirmed the backing endpoint (`GET /api/users`) has zero search/pagination/filtering; (2) ~8-9 modals behave like a mini-app trapped in a popup (internal tab state, nested sub-modals spawning more modals, or a whole page component embedded in an overlay) rather than a simple create/edit/confirm form.

**Explicit scope boundary, stated up front**: this fix does NOT remove the app's eager "load the whole user table into `db.users` on login" pattern (`src/lib/store.tsx`'s `fetchFullDB`) — every existing screen reads from that global client-side cache, and detaching it is a much larger refactor than what was asked. This phase adds a proper searched/paginated path for the specific pickers that need it and leaves the rest of the app's existing `db.users`-reading screens untouched. Document this boundary in the final report — it's a known, real limitation worth a dedicated future pass at higher real-world scale, not silently glossed over.

**Routing decision (finalized)**: the whole logged-in app currently lives at one route, `/portal`, with `Portal.tsx` switching between modules via internal `active`/`setActive` state — no nested React Router routes exist below `/portal`. Restructuring `Portal.tsx` itself to host an `<Outlet>`-based nested-route layout (keeping the sidebar visible on detail pages) is a deeper change than this fix's scope — `Portal.tsx` is a large, actively-maintained file and that refactor is a bigger, separate project. Instead: each converted page is a **standalone top-level route** directly under `/portal/*` in `src/App.tsx` (sibling to `/portal` itself, both behind the same `<Guard>`), with its OWN minimal header — reuse the exact chrome pattern `src/pages/Login.tsx` already establishes (`Logo` + `ThemeToggle` + a "Back" link, see its header JSX) rather than inventing a new layout. This trades away the persistent sidebar on these specific detail views in exchange for a real bookmarkable URL, working browser-back, and no stacked-modal problem — an accepted, common enterprise pattern for drill-down detail views (issue trackers, admin consoles, etc. routinely drop the main nav one level deep). The "Back" control on each new page returns to a sensible parent (e.g. `navigate(-1)`, or an explicit known list route/portal-tab if that's more reliable — agent's call per page, document which). Existing sidebar `Mod` entries and `Portal.tsx`'s tab system are otherwise completely untouched. Trigger sites (a row's "view" button, etc.) switch from `setXOpen(true)` to `navigate('/portal/...')`.

## Phase A — Foundations: search endpoint + AsyncEntityPicker component

**Backend** (`server/src/routes/users.ts` or a new dedicated search endpoint):
- Add `GET /api/users/search?q=&role=&classId=&limit=&cursor=` — `q` matches name/email (case-insensitive `contains`), `role` filters (student/teacher/staff/parent/admin), `classId` optionally narrows students to one class (via `Enrollment`), paginated (`limit` default 20 max 50, cursor-based matching the existing pagination convention already used elsewhere in this codebase — check `server/src/lib/pagination.ts` or wherever the existing cursor pattern lives, e.g. audit log/messages/notifications/fee invoices from Phase 10, and reuse it exactly). Response includes disambiguating context per row: for a student, class/section label + roll number; for staff/teacher, `employeeId` + department/designation. `requireAuth` only (every role needs to search for *something* — a parent doesn't need this, but staff/teachers/admins do across many forms) — do not over-restrict, but do scope to `schoolId` like every other endpoint.
- Keep `GET /api/users` (the existing full-list endpoint) exactly as-is — many existing screens depend on it via `db.users`; this is additive, not a replacement.

**Frontend**:
- `src/lib/hooks/useEntitySearch.ts` — a debounced (≈300ms) hook wrapping the new search endpoint, cancels stale requests, returns `{results, loading}`.
- `src/portal/ui.tsx` (or a new `src/portal/components/AsyncEntityPicker.tsx` if `ui.tsx` is getting large — your call after reading it) — a reusable `AsyncEntityPicker` component: text input, debounced search-as-you-type, a real dropdown result list (not `<datalist>` — build a proper positioned listbox with keyboard nav: arrow keys + Enter + Escape, click-outside-to-close, matching this app's existing `Modal`/`Field` visual language), each result row shows name + the disambiguating context string, selecting one sets the controlled `value`/calls `onChange(id, label)`. Props: `role` (or `roles[]`), optional `classId` filter, `value`, `onChange`, `placeholder`, `label`. Loading/empty/error states handled inline, not via a toast.
- Do NOT modify `SearchableUserPicker` (`employee.tsx`) — leave it as-is for its existing 6 call sites (it's adequate for the smaller, bounded staff-search use cases it's already used for); `AsyncEntityPicker` is the new, more capable component for the unbounded cases.

**Verification**: full quality gate (frontend tsc/eslint, backend tsc/tests), plus a live proof-of-concept — retrofit exactly ONE existing flat-select picker (suggest: `finance.tsx`'s fee-invoice student picker, since Finance is money-critical and a good stress test) to use the new component, live-verify search-as-you-type actually narrows results against real seeded data, and confirm keyboard navigation works.

## Phase C — Convert modal-as-mini-app cases to real pages (tier 1, highest confidence)

New routes under `/portal/*` (see routing decision above):

1. `EmployeeDetailModal` (`employee.tsx`) → `/portal/employees/:id` — the 3 existing tabs (Overview/History/Documents) become real tab state on the page (or, cleaner, `/portal/employees/:id/history` and `/portal/employees/:id/documents` as further nested routes — your call, document which you chose and why).
2. `BookDetailModal` (`library.tsx`) → `/portal/library/books/:id` — copies list + add/edit/delete-copy become inline page sections/rows with their own small confirm dialogs (a single-level confirm modal is fine; the point is eliminating the outer-detail-modal-spawning-inner-modal stack, not banning all modals).
3. `ItemDetailModal` (`inventory.tsx`) → `/portal/inventory/items/:id` — same principle: adjust-stock/edit/delete become page actions, not nested modals.
4. `PODetailModal` (`inventory.tsx`) → `/portal/inventory/purchase-orders/:id` — receive-PO becomes a page section or a single non-nested confirm/receive form.
5. `ChapterManagerModal` (`academic.tsx`) → `/portal/academic/subjects/:id/chapters`.
6. "Subjects & teachers" modal (`academic.tsx`, inside `ClassesMod`) → `/portal/academic/classes/:id/subjects`.
7. "Roster" modal (`academic.tsx`, inside `ClassesMod`) → `/portal/academic/classes/:id/roster`.
8. `<Modal title="Student Profile Report">` wrapping `StudentReportMod` (`office.tsx`) → just navigate to a route that renders `StudentReportMod` directly, e.g. `/portal/students/:id/report` (the component itself needs no changes, only its trigger site and wrapper).

Each conversion: read the modal's current trigger site(s) (there may be more than one per case — check thoroughly, e.g. `EmployeeDetailModal` is opened from `MyTeamMod`, the People screen, AND possibly elsewhere), replace `setXOpen(true)`/`setXId(id)` with `navigate(`/portal/...`)`, build the new page component (can literally be the modal's existing inner JSX moved into a page shell — don't rewrite the actual form/data logic, just the chrome around it), add the route in `src/App.tsx` nested under the `/portal` `Guard`, remove the old modal wrapper once its replacement route works. Add a "Back" affordance (a simple `<ArrowLeft>` + `navigate(-1)` button in the new page's header, matching existing conventions like `Login.tsx`'s "Back to site" link).

**Verification**: full quality gate + live Playwright verification per conversion — navigate to the URL directly (confirms it's real, bookmarkable), confirm browser back-button returns to the origin list correctly, confirm the page's actual functionality (e.g. add/edit/delete a book copy) still works identically to before.

## Ground rules for every phase
