# Phase 23 — Parent Experience

Independent of Phase 20/22, can run in parallel with Phase 24. Depends loosely on Phase 21 (fee installment UI, item 4) — build that item last within this phase, after confirming Phase 21's installment-plan endpoints are live; everything else in this phase has no dependency.

## 1. Family view — the main item

Confirmed by code read: a parent with multiple children currently picks ONE ward at a time via `WardPicker` everywhere (`src/portal/modules/viewer.ts`'s `useWard()`, used in 9+ places). This phase does NOT remove per-ward detail screens — those stay. It ADDS a genuine combined view.

- **No new backend model needed** — this is an aggregation problem, not new data. Add `GET /api/parents/me/family-summary` (parent-only): for every ward returned by the existing `useViewedStudents()`-equivalent server logic, aggregate: today's attendance status, any homework due this week, total fee due across all their invoices, next 3 upcoming calendar events relevant to any ward's class, and (once Phase 18 exists) each ward's syllabus pace headline for their core subjects. This is a read-only, multi-query aggregation endpoint — reuse existing per-domain query functions (attendance summary, invoices, homework), don't reimplement their logic, just call them for each ward and combine.
- Frontend: a genuinely new **Family Overview** screen (not a replacement for existing per-ward screens) — cards or a table, one row/section per child, the aggregated snapshot above, with a click-through to that child's existing detail screens. This becomes the parent's natural landing page — consider whether it should replace or supplement the existing `Overview` dashboard for the parent role (read `Portal.tsx`'s existing parent `Overview` rendering first; augmenting it with a multi-ward section is probably cleaner than a fully separate screen, but that's a judgment call to make after looking at the current layout).

## 2. Daily "my child today" digest

- A scheduled (or on-demand-triggered, since this codebase has no existing cron/scheduler infrastructure — check first, and if none exists, build this as a manually-triggerable endpoint plus document that real scheduling needs an external cron hitting it, e.g. a simple `node-cron` addition or documenting a system cron calling a protected endpoint — don't over-engineer a full job-scheduling system for one feature) digest per parent: reuses the family-summary aggregation from item 1, formats it as a notification (push + the existing in-app notification system), one notification per parent per day, not per ward.
- `POST /api/parents/digest/send-now` (admin/superadmin, for testing/manual trigger) and the actual scheduled version — check `server/src/lib/notify.ts` and see if there's a sensible place to hook a daily job; if truly no scheduler infrastructure exists in this codebase, implement the send logic as a well-tested function and a callable endpoint, and clearly document in the code and your report that production deployment needs an external scheduler (cron, or a hosting platform's scheduled-function feature) to call it daily — don't fake a working cron that doesn't actually run anywhere.

## 3. WhatsApp notification channel

- Extend `server/src/lib/notify.ts` with a `sendWhatsApp(msg: WhatsAppMessage)` function following the **exact existing pattern** for `sendEmail`/`sendSms` (a `whatsappProvider()` selector based on an env var's presence, e.g. `WHATSAPP_API_KEY` + `WHATSAPP_PHONE_NUMBER_ID` for a real Meta Cloud API integration, defaulting to `console` log when unset — never throws, best-effort). **Be explicit in your report and in a code comment that this is a provider abstraction only** — there is no real WhatsApp Business API account to test against, so "real and working end-to-end" for this specific item means "the abstraction is real and correctly wired into every place email/SMS already fire from," not "messages actually arrive on WhatsApp," which requires credentials nobody has yet.
- Wire it into the same call sites email/SMS already fire from (fee reminders, admission credentials, leave decisions, etc. — check the existing `sendEmail`/`sendSms` call sites from Phase 9 and add the WhatsApp call alongside each, matching the existing multi-channel best-effort pattern) plus the new daily digest from item 2.
- Add `WHATSAPP_API_KEY`/`WHATSAPP_PHONE_NUMBER_ID` (or whatever the real Meta Cloud API requires — check their actual API shape if you have any way to verify it, otherwise use a reasonable placeholder shape and document the assumption) to `server/.env.example` with the same "optional, degrades gracefully" documentation style already used for the other providers.

## 4. Fee installment parent UI

Only build this after confirming Phase 21's installment-plan backend is live (check `git log`/`git status`/the running server for `server/src/modules/fees/` changes, or directly test `GET /api/fees/...` for installment-related fields). Frontend-only: at the point a parent would otherwise see one lump invoice (the existing Payment Gateway screen, `src/portal/modules/paymentGateway.tsx`), if an installment plan applies, show the staggered schedule instead and let them pay each installment as its own invoice through the existing, unmodified payment flow.

## Ground rules
Same as every previous phase: additive migrations only if truly needed (item 1/2 should mostly be new service functions, not new tables — a digest doesn't need to persist anything beyond "last sent" bookkeeping if you want to avoid duplicate sends, which is a reasonable small addition), `requireRole()`/scope helpers, `HttpError`, `audit()` where mutations exist, no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent, full tsc/eslint/87-test verification, live curl+UI verification of the family-summary aggregation against a real multi-ward parent in the sample data (confirm the seed data actually has a parent with 2+ wards — check first, add one to sample data if not).
