# Phase 30 — Canteen Prepaid Wallet

Independent, self-contained — can run in parallel with Phase 29. Ties into the real GL (Phase 17) for accounting and reuses the existing QR/barcode pattern already established for library book copies (`BookCopy.barcode`) and staff ID documents (`server/src/modules/employeeDocuments/`, which already draws a QR via `qrText` in its PDF helper — read that for the exact QR-rendering approach to reuse, don't add a new QR library if one's already in use).

**Scope note**: there is currently no student-facing QR/ID-card infrastructure in this codebase (only staff documents have one). This phase needs to add a minimal student ID identifier — don't build a whole new "ID card system," just enough to uniquely and scannably identify a student at a canteen point-of-sale.

## 1. Data model

- `StudentWallet { id, schoolId, studentId (unique — one wallet per student), balance (integer paise, matching the GL's integer-cents/paise convention from Phase 17 — never a float), pinHash? (optional PIN for topping up in person or for parent-authorized spend limits — keep simple, a nullable field, don't force this if it adds complexity beyond what's needed), createdAt, updatedAt }`.
- `WalletTransaction { id, schoolId, walletId, type (TopUp|Purchase|Refund|Adjustment), amount (signed integer paise — positive for top-up/refund, negative for purchase, so balance is always derivable as a running sum, matching the ledger-not-mutable-total pattern already used elsewhere), reason?, itemsSummary? (free text, e.g. "2x Samosa, 1x Juice" — no need for a full canteen POS item-catalog model unless trivial, keep v1 simple), recordedById, occurredAt, relatedInvoiceId? (if a top-up is itself billed as a fee item rather than paid directly, check with the Fees module for the cleanest connection — likely top-ups are a direct payment via the existing Payment Gateway, not a fee invoice, verify which makes more sense given how `server/src/modules/fees/` and the payment-gateway integration already work before deciding) }`.
- Student QR identifier: reuse the existing `User.id`/`employeeId`-equivalent-for-students pattern — check if `Student`/`Enrollment` already has a stable unique reference number (roll number, admission number) suitable to encode in a QR (`EduNova student <admissionNo>`, matching the staff QR's exact text-encoding convention) rather than adding a new ID field if one already exists.

## 2. Wallet operations

- `POST /api/canteen/wallets/:studentId/topup` `{amount, method}` — parent/guardian (for their ward) or staff/admin (in-person top-up) initiates. If via the existing online Payment Gateway, reuse that exact payment flow (don't build a parallel payment integration) and only credit the wallet on confirmed payment success (mirror how fee payments already confirm before marking paid — check that flow's confirmation-webhook-or-callback pattern and reuse it exactly). **On successful top-up, post to the GL** (Phase 17): debit Bank/Cash, credit a "Canteen Wallet Liability" account (a top-up is money held on the school's behalf, not yet revenue — standard treatment, don't post it as revenue at top-up time).
- `POST /api/canteen/wallets/:studentId/purchase` `{amount, itemsSummary?}` — canteen staff (check if a dedicated canteen-staff role/designation exists; if not, use `staff` role and note the same role-granularity limitation Phase 22 already flagged for gate-security) scans the student's QR (or enters admission number manually as a fallback for a broken/missing scanner) and records a purchase: reject with a clear error if `balance < amount` (no overdraft, no negative balances — this is a prepaid wallet, not credit). **On purchase, post to the GL**: debit the Canteen Wallet Liability account, credit real Canteen Revenue — this is the point where the money actually becomes the school's recognized revenue, matching proper accrual treatment for a prepaid-balance system.
- `GET /api/canteen/wallets/:studentId` — current balance + recent transactions (self/guardian, staff/admin, canteen-staff for balance-check-before-purchase only — don't expose full transaction history to canteen counter staff beyond what's needed to complete a sale, that's a minor but real privacy consideration, current balance is enough for them).
- `GET /api/canteen/wallets/:studentId/transactions?from=&to=` — full spend log (self/guardian, staff/admin) — this is the parent-facing "spend log" from the roadmap description, make sure it's genuinely usable (dated, itemized, running balance shown per row).

## 3. Frontend

- Parent-facing: a wallet balance card + top-up flow (reusing the existing Payment Gateway UI pattern) + spend log, likely a natural fit on the existing parent dashboard or fee/payments area — check `src/portal/modules/paymentGateway.tsx` and the parent `Overview` for where this fits most naturally (could piggyback on Phase 23's Family Overview if that's landed by the time this phase builds — check first).
- Canteen-staff-facing: a simple point-of-sale screen — scan/enter student ID, show current balance, enter purchase amount, confirm (reject clearly if insufficient balance).
- Student-facing (if students have their own login and it's appropriate): a simple balance + recent-spend view, read-only.
- Admin-facing: a reconciliation view (total wallet liability outstanding across all students — should tie to the GL's Canteen Wallet Liability account balance, a genuinely useful correctness check: sum of all wallet balances should equal that GL account's balance at any point, verify this explicitly as part of testing).

## Ground rules
Same as every previous phase: additive migrations, `server/src/modules/canteen/{router,service,schema}.ts`, zod validation, `requireRole()`/scope helpers (self-or-guardian for wallet viewing, matching the pattern used everywhere else in this codebase), `HttpError`, `audit()` on every wallet mutation (top-up, purchase, adjustment — this is real money, same seriousness as Phase 21's scholarship approvals), add a Phase 30 cleanup block to `POST /reset` for `StudentWallet` and `WalletTransaction`, no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent, full tsc/eslint/87-test verification, live curl+UI verification — specifically: top up a real seeded student's wallet, make a purchase that succeeds, attempt a purchase that exceeds balance and confirm it's cleanly rejected (never allowed to go negative), and confirm the GL posting is correct at each step by re-running the Phase 17 whole-ledger-balance check plus the specific reconciliation check that sum-of-wallet-balances equals the Canteen Wallet Liability account balance.
