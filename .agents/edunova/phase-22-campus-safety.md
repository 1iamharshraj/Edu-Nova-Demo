# Phase 22 — Campus Safety & Security

Independent of every other phase in this roadmap except reusing existing infrastructure (health records, files, notifications). Can run in parallel with Phase 20.

## 1. Authorized pickup + parent OTP approval

- `AuthorizedPickupPerson { id, schoolId, studentId, name, relation, phone, photoFileId?, addedById, active }` — per-student list of people allowed to collect them, managed by the parent/guardian or staff/admin.
- `PickupEvent { id, schoolId, studentId, pickedUpByName, pickedUpByRelation, pickupType (Regular|EarlyOrUnlisted), approvedByOtp (bool), otpVerifiedAt?, recordedById, recordedAt }` — staff/gate-security logs every pickup. If the person collecting ISN'T on the authorized list, or it's an early pickup outside normal dismissal, require an OTP step: `POST /pickup-events/:id/request-otp` generates a short-lived code and sends it to the parent via the existing notify infrastructure (push/email/SMS — reuse `server/src/lib/notify.ts`, don't build new delivery), `POST /pickup-events/:id/verify-otp {code}` confirms it before the pickup event is marked complete. A pickup that never gets OTP-verified when required should be clearly flagged, not silently allowed through.
- Endpoints: `/api/safety/authorized-pickups` CRUD (parent for their own ward, staff/admin for any), `/api/safety/pickup-events` (create/list, staff/admin/gate-role — check if a dedicated "security/gate" role exists; if not, use `staff` and note this as a role-granularity limitation worth a future dedicated role), the OTP request/verify actions above.
- Frontend: parent-facing "Authorized Pickup" list management (add/remove people, with a photo if convenient), staff-facing "Log a pickup" screen with the OTP flow, and a simple daily pickup log view.

## 2. Visitor management

- `Visitor { id, schoolId, name, phone, purpose, hostUserId? (who they're visiting, nullable), checkInAt, checkOutAt?, badgeNo?, recordedById }`.
- `/api/safety/visitors` — create (check-in), `POST /:id/checkout`, list (filterable by date, currently-checked-in). Staff/admin only.
- Frontend: a simple front-desk check-in/check-out screen, and a "currently on campus" list.

## 3. Confidential counseling + anonymous reporting

**This is the most sensitive data model in this entire roadmap — read carefully before implementing.**

- `CounselingRecord { id, schoolId, studentId, counselorId, sessionDate, notes, category?, followUpNeeded (bool) }` — visibility MUST be strictly limited to: the specific counselor who created it, and optionally the principal/superadmin **only if the school has explicitly designated a counselor-oversight role** (default to counselor-only if no such designation exists — do not default to admin-visible). This is deliberately MORE restricted than `HealthRecord` (which is visible to class teachers) and MORE restricted than `StaffConductRecord` (Phase 11, HR/admin) — do not reuse either's RBAC pattern, write a dedicated, narrower check. **Not visible to class teachers, not visible to staff, not visible to the student themselves, not visible to parents, unless the counselor explicitly shares something (out of scope for this phase — don't build a sharing mechanism, keep it fully closed by default).**
- A `counselor` capability needs to exist on a `User` — check if a boolean flag or a dedicated designation field makes more sense given the existing `User.designation`/`User.department` free-text fields; a simple approach is checking `designation` contains "Counselor" is fragile — prefer a proper boolean `User.isCounselor` field (additive migration) set by admin, and gate the module on that flag rather than a specific role string.
- `AnonymousReport { id, schoolId, category (Bullying|Safety|Wellbeing|Other), description, submittedAt, status (New|Reviewing|Resolved), reviewedById?, resolutionNotes? }` — **genuinely anonymous**: no `submittedById` field at all, not even a hidden one. Submittable by any student/parent (no auth-identifying info stored), reviewable/resolvable by counselor + principal/superadmin only.
- Endpoints: `/api/safety/counseling-records` (counselor-only CRUD, strictly scoped as above), `/api/safety/anonymous-reports` (`POST` open to any authenticated student/parent but deliberately not linked to their identity in storage; `GET`/`PATCH` counselor + principal/superadmin only).
- Frontend: a counselor-only module for counseling records, a simple "Report a concern" form reachable from student/parent navigation (clearly labeled as anonymous), and a review queue for counselors/principal.

## 4. Medication log + allergy alerts

- Extends the existing `HealthRecord` model/module (Phase 8) rather than forking a new one — check `server/src/modules/health/` first. Add a `MedicationSchedule { id, schoolId, studentId, medicationName, dosage, timesPerDay (or specific times, JSON array), startDate, endDate?, notes?, addedById }` and `MedicationLog { id, schoolId, scheduleId, administeredAt, administeredById, notes? }` for the nurse/staff to log each actual dose given — this is new (a schedule + an administration log is a different concept from a health record entry), but the RBAC/visibility rules should match `HealthRecord`'s existing pattern exactly (student/guardians/class-teacher/staff/admin), reusing whatever scope helper Phase 8 already built rather than reimplementing.
- **Allergy alerts**: if `HealthRecord` already has an `Allergy` kind (check Phase 8's `HealthKind` enum), surface it prominently wherever relevant — the frontend agent should check the health record UI, the student profile/report, and (if Phase 24's hostel mess or any meal-related screen exists yet) meal-planning screens, for a clear allergy badge. This is mostly a frontend surfacing task, not new backend data, once the allergy kind is confirmed to already exist.

## Ground rules
Same as every previous phase: additive migrations, `server/src/modules/safety/{router,service,schema}.ts` for items 1-2, extend `server/src/modules/health/` or a clearly-separated `server/src/modules/counseling/` for item 3 (your call based on how cleanly it fits — given the very different RBAC, a separate module is probably cleaner, don't force it into `health/`), extend `server/src/modules/health/` for item 4, zod validation, `requireRole()`/scope helpers, `HttpError`, `audit()` on mutations (item 3's counseling records should still be audited for who-accessed-what even though the DATA itself is restricted — an audit trail of access is a safety feature, not a leak), add cleanup blocks to `POST /reset`, no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent, full tsc/eslint/87-test verification. **Before reporting done, specifically live-test that a non-counselor staff/admin account gets 403 on counseling-record endpoints**, and that an anonymous report genuinely contains no identifying trace of its submitter in the stored row or the audit log entry for its creation.
