# Phase T2 — Strong Admissions (Part A + Part B)

Second phase of the Advanced Timetable Generation project (`advanced-timetable-roadmap.md` — read in full first, especially D4 and D9). This is one of the two or three largest phases in the whole roadmap — real India-specific quota/reservation and physical-document-custody management, not just a data-model tweak. Read the existing `Application`/`Certificate` models and `server/src/modules/applications/` module THOROUGHLY first (confirmed current shape: `Application.documents` is a flat `File.id[]` with zero metadata — no type, no physical-custody concept, no conditional-requirement logic at all today). This phase is a strict superset of what exists — the current admission→approve→create-student-atomically flow must keep working exactly as it does today for a school that doesn't touch any of the new fields.

## Part A — Admission data expansion

Extend `Application` (additive fields, or a new 1:1 `AdmissionProfile` table if the field count makes that cleaner — your call when building, document which):

- **Prior academics**: `previousSchoolName`, `previousBoardId` (nullable FK to `Board`, since the applicant's prior board may differ from this school's), `lastGradeCompleted`, and a new `PriorSubjectScore { applicationId, subjectName (free text — prior school's subject naming won't match this school's `Subject` catalog), score, maxScore }` — individual key-subject scores, not just one aggregate, since T3's `TrackEligibilityRule` needs subject-specific thresholds (e.g. "Math ≥ 80"). Marksheet document upload via the Part B document system below (kind=`PREVIOUS_MARKSHEET`).
- **Track/stream preference**: `declaredTrackPreference` (free text or a school-configurable enum — check whether `Stream`/track concepts exist as an editable catalog already; if not, keep this simple free text for T2 and let T3 formalize it against real `Cohort`/track data). The actual eligibility check against `TrackEligibilityRule` is T3's job — T2 only needs to capture the declared preference and the scores that feed it; do not attempt to implement the eligibility check itself in this phase, that's out of scope until T3's rules exist. Leave an obvious, documented hook point.
- **Sibling linkage**: before adding a new field, verify siblings are already derivable via shared `Guardian` records (query: does another active student share a `Guardian` row/contact with this applicant's declared guardian info?). If yes, implement this as a *lookup/suggestion* at application time ("possible sibling: Aarav Sharma, X-A — link?") rather than a redundant new relationship field. If genuinely not derivable as-is, add `siblingStudentId` (nullable FK to `User`).
- **Category/quota**: `AdmissionCategory { id, schoolId, name, code, requiresCertificate (bool) }` — a school-editable catalog, NOT a hardcoded enum (reservation category names vary by state/school-type in India — General/SC/ST/OBC/EWS/RTE/Management/Staff-Ward/Sports-Talent/Minority/Defense are a reasonable seeded default set, but the school must be able to add/rename/retire categories). `Application.admissionCategoryId` (nullable FK). This category drives which document types are required in Part B.
- **Health flags at intake**: a small structured subset (known allergies, known conditions, blood group if collected) — NOT a full duplicate of Phase 8's `HealthRecord`. On admission approval (the existing atomic student-creation transaction), if any health flags were captured, create the corresponding `HealthRecord` row(s) as part of that same transaction — capture once, hand off once, never a second data-entry pass for the family.
- **Transport requirement**: a simple "needs transport: yes/no + preferred area/stop if known" capture — on approval, if yes, surface it as a to-do for staff to complete the actual `StudentStopAssignment` (Phase 12) post-enrollment; don't try to auto-match a stop from free-text at this phase, that's a staff task the capture just makes visible.
- Approval flow (`approve()` in the applications service) stays otherwise unchanged — still creates student+parent+enrollment+guardian in one transaction; this phase only adds what gets captured before that point and what gets handed off at that point.

## Part B — Document & certificate management with physical custody

This is the deep new subsystem the user explicitly asked for.

- **`RequiredDocumentType { id, schoolId, name, code, conditionExpression (or a simpler structured condition — see below), isActive }`** — a school-configurable catalog, seeded with a real default set: Birth Certificate, Transfer Certificate (previous school), Previous-school report cards/mark sheets, Migration Certificate, Character Certificate, Aadhaar card copy, passport photographs, address proof, Caste Certificate, Income Certificate, Domicile/Residence Certificate, Disability Certificate, Minority Certificate, RTE Allotment Letter, Medical/Immunization/Fitness Certificate, Bank Passbook copy, Sports/Extracurricular Achievement Certificates, parent ID/employment proof, previous school's Fee Clearance/No-Dues Certificate, and a generic Declaration/Undertaking type. **Condition model**: keep this simple and structured, not a free-text expression language — e.g. `{ requiredIfCategoryIn: string[] (AdmissionCategory codes), requiredIfAdmissionMode: string[] (e.g. RTE), requiredIfBoardChanged: bool, alwaysRequired: bool }`. Compute "is this document required for THIS application" by evaluating these simple flags against the application's actual category/mode/board-change status — no expression parser needed.
- **`SubmittedDocument { id, schoolId, applicationId (or studentId, post-enrollment — support both since documents can be added after admission too), requiredDocumentTypeId (nullable — some submissions won't map to a catalog type), fileId (nullable FK to existing File, for a digital scan), isOriginal (bool), physicalLocationRoom, physicalLocationShelf, physicalLocationFolder (free text, simple structured location — NOT the same Room entity used for classrooms), receivedDate, status (HELD|RETURNED|LOST|NOT_APPLICABLE), returnedDate, returnedTo, returnReason }`.
- **Completeness checklist**: on the Application detail view, compute and show every required document type (per the condition evaluation above) against what's actually been submitted — clear "collected" vs "missing" status. `School`-level setting: `admissionDocumentsBlockApproval` (bool) — if true, missing hard-required documents block the Approve action; if false, approval proceeds with a visible warning and the checklist stays open post-enrollment.
- **TC-issuance document-return workflow**: extend the existing TC issuance flow (`Certificate kind=TC`, in `server/src/modules/applications/` or `certificates/` — check which module owns TC issuance) so that issuing a TC for a student first surfaces every `SubmittedDocument` for that student where `isOriginal=true AND status=HELD`. Issuance requires either marking each as `RETURNED` (capturing `returnedTo`) or an explicit staff-acknowledged exception per document (with a reason) — never silently proceed past held originals without an explicit decision either way.
- **Records report**: a simple staff-facing screen/endpoint — "which original documents are currently held, for which students, physically located where" — filterable by room/shelf, useful for actual records-room audits, not just a compliance checkbox.

## Ground rules
Same rigor as every other phase: additive migrations only, zod validation, `requireRole()` (staff/admin for document management, matches existing Applications RBAC), `HttpError`, `audit()` on every document status change (received/returned/lost — this is compliance-relevant), add reset-cleanup blocks to `POST /reset` for every new table (FK-safe order — `SubmittedDocument`/`PriorSubjectScore` before `Application`, `AdmissionCategory`/`RequiredDocumentType` are school-level catalogs cleaned like other catalogs), full `tsc`/`eslint`/`npm test` gate clean, no git commands, no `/admin/reset`/`/admin/load-sample-data` except a final verification step.

**Live verification required, not optional**: run a real admission through the full lifecycle — submit an application with a declared category requiring specific documents, confirm the completeness checklist correctly shows missing items, submit the documents (with physical location for originals), approve the admission (confirm health/transport handoff actually creates the right downstream rows), then later issue a TC for that same student and confirm the document-return checklist correctly surfaces every held original and blocks/warns appropriately until resolved.

**Testing bar** (per roadmap D9): live UI verification in a real browser for the completeness checklist and the TC-return checklist specifically — these are exactly the kind of dense, multi-state screens where a wrong popup-vs-page call would hurt; make and document that judgment call.
