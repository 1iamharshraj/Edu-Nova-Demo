# Phase 28 — Multi-School / Group Management

**The most architecturally significant phase in this roadmap.** Runs alone, with a dedicated design pass (this spec IS that design pass — read it fully before touching code, and if implementation reveals the design below doesn't hold up against the real schema, stop and reconsider rather than forcing it, the same caution Phase 17/Accounting got).

## Why this is different from every other phase

Confirmed by code read: `School` (`server/prisma/schema.prisma` line 10) is the root multi-tenancy boundary — every single domain model in this 97-model schema hangs off `schoolId`, and `Ctx.schoolId` (the request-scoping context used by every module's `requireRole()`/scope check) assumes exactly one school per request, resolved from the logged-in user's own `schoolId`. There is currently NO concept of a user who legitimately needs data from MORE THAN ONE `School` row in a single session. This phase adds that, for real trust/group deployments (a management trust running 3-10 campuses, each its own `School` tenant, wanting cross-campus comparison).

**Explicit non-goal**: this phase does NOT merge schools into one shared tenant, does NOT let a group-admin write into another school's operational data (create a student, mark attendance, etc. — that stays strictly per-school, per-school-staff), and does NOT change how any existing single-school user or endpoint works. It ADDS a narrow, strictly-read-only cross-school aggregation layer plus a new relationship model, and everything else in the 97-model schema is untouched.

## 1. Data model

- `SchoolGroup { id, name, createdAt }` — the trust/group entity, standalone (not itself a `School` — deliberately NOT reusing `School` as a "parent tenant," which would be tempting but wrong: a group isn't a school, it has no classes/students/staff of its own, don't force-fit it into the existing tenant model).
- `School.groupId String?` (nullable — most schools using this ERP are standalone, additive migration, backward compatible for every existing school).
- `GroupAdmin { id, groupId, userId, role ('GroupAdmin' | 'GroupViewer') }` — a user granted cross-school access. **Critical decision**: a group-admin is NOT necessarily also a `User` row with `schoolId` set to any of the member schools — they may be a trust-level employee with no operational account at any single campus. So `GroupAdmin.userId` references a `User` row, but that `User` row's own `schoolId` can be ANY school (even one not in the group, e.g. a dedicated trust-HQ pseudo-school) — the group-membership grant is what matters, not their home school. Read how `Ctx`/`requireRole()` currently resolves scope (`server/src/lib/rbac.ts` or wherever `Ctx` is built) before deciding the cleanest way to let a request additionally carry "acting as group-admin for group X" — likely a new middleware/ctx-augmentation step that runs ONLY on `/api/group/*` routes, checking `GroupAdmin` membership explicitly rather than touching the existing single-school `Ctx` resolution path used by every other route. Do not weaken or complicate the existing single-school scope-check that every other module depends on — this must be additive and isolated.

## 2. Read-only cross-campus aggregation endpoints

All under `/api/group/*`, gated by the new group-admin check (not the existing `requireRole()` role strings — a separate, explicit `assertGroupAccess(ctx, groupId)` check), all strictly read-only:
- `GET /api/group/:groupId/schools` — member schools list.
- `GET /api/group/:groupId/overview?termId=` — per-school: fee collection % (reuse Phase 17/Fees aggregate query, run once per member school), attendance % (reuse existing attendance aggregate), syllabus pace summary (reuse Phase 18/19's aggregation — average "on pace" vs "behind" across classes), teacher load (reuse Phase 19's workload query). One row per school, side by side for comparison. This is N sequential/parallel calls into each school's already-existing single-school aggregate functions, NOT a new cross-school SQL join — reuse the real per-school service functions from Fees/Attendance/Syllabus/Analytics, called once per member school with that school's own `schoolId`, then combine the results in the group router. This keeps the strict per-school data isolation intact (no query ever spans two schools' rows at once) while still delivering the comparison view.
- `GET /api/group/:groupId/school/:schoolId/drilldown?...` — if the overview reveals a school needs a closer look, a read-only pass-through to that school's own existing detail endpoints, scoped by the group-admin check instead of that school's own staff/admin role check. Be conservative here — only expose read endpoints that already exist and are safe to expose read-only (fee reports, attendance reports, syllabus reports), do not expose raw student PII lists cross-school without a clear reason; if in doubt, leave a drilldown item out rather than over-expose.

## 3. Admin management of groups

- `POST /api/group` (superadmin only, and only a superadmin of... which school? This needs a decision: since `SchoolGroup` is not itself a tenant, creating one is a platform-level action — restrict it to a superadmin of ANY school for now, since there's no higher "platform admin" concept in this codebase yet, and document this as a known limitation worth a dedicated platform-admin role in a future phase, don't invent one now) `{name}`, `POST /api/group/:id/schools` (add a School to a group — superadmin of that specific School only, to prevent someone claiming another school into their group without that school's own admin consent), `POST /api/group/:id/admins` (grant `GroupAdmin`/`GroupViewer` to a user — group's existing admins only).
- Frontend: a new top-level "Group" area (only visible to users with any `GroupAdmin`/`GroupViewer` membership — check `Portal.tsx`'s existing role-gating pattern for how to add a non-standard-role-gated section, since this isn't gated by the normal `role` field), showing the cross-campus overview table/comparison charts and, for regular per-school admins, a simple "which group is my school part of" indicator plus the school-creation/join flow.

## Ground rules
Same as every previous phase but with extra care given the architectural weight: additive migrations only (`SchoolGroup`, `School.groupId`, `GroupAdmin` — zero changes to any existing model's required fields or existing query behavior), `server/src/modules/group/{router,service,schema}.ts`, zod validation, the new `assertGroupAccess` helper kept fully separate from the existing `requireRole()`/`Ctx` scope system (additive, not a modification to shared scope code every other module depends on), `HttpError`, `audit()` on every mutation (group creation, school added to group, admin granted — these are consequential actions), add a Phase 28 cleanup block to `POST /reset` for `GroupAdmin` and `SchoolGroup` (and null out `School.groupId` — but note `POST /reset` is scoped to ONE school today, check whether it needs to become group-aware or whether nulling just the current school's `groupId` and leaving the `SchoolGroup`/other member schools alone is correct — likely the latter, a reset of one campus shouldn't destroy the whole group), no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent, full tsc/eslint/87-test verification (this phase touches shared scope-adjacent code — run the FULL existing test suite carefully, not just spot checks, to confirm zero regression to any existing single-school role/scope behavior), live curl+UI verification — specifically: create a group with 2+ of the existing seeded/test schools (or create a second throwaway school via whatever the existing school-creation path is, if only one exists in dev — check first), confirm a group-admin sees a correct side-by-side comparison, confirm a NON-group-admin user gets 403 on every `/api/group/*` route, and confirm every existing single-school endpoint's behavior is completely unchanged (spot-check a regular admin login, a regular teacher login, and a regular student login against a handful of pre-existing endpoints to prove no regression).
