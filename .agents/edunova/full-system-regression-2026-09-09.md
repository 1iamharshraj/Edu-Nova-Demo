# Full-System Regression — 2026-09-09

Final step of the advanced-features build mandate ("test every other feature of our ERP system too"), once all 13 phases of `phase-18-plus-advanced-roadmap.md` (Phases 18–30) landed. Mirrors the original `deep-audit-2026-09-08.md` pattern: parallel domain-audit agents, each doing real live testing (curl + Playwright, not code-only review) against the running dev server, covering every phase from 0 through 30.

## Audit structure

Six parallel agents, each covering a cluster of phases:

1. Core academic, admissions, identity — Phases 0, 1, 1b, 2, 3, 4
2. Finance, HR, employee management — Phases 5, 6, 11, 17, 21, 30
3. Communication, welfare, safety, compliance — Phases 7, 8, 9, 22, 29
4. Transport, alumni, hostel, library, inventory, culture — Phases 12, 13, 14, 15, 16, 24, 27
5. Syllabus, analytics, exam ops, timetable auto-generation — Phases 18, 19, 25, 26
6. Parent experience, multi-school groups, cross-cutting RBAC/reset sweep — Phases 23, 28, plus a full read of every `POST /admin/reset` cleanup block against all ~130 Prisma models

Operational note: with six agents hitting the same shared dev server concurrently, the `/api/auth/login` rate limiter (10/15min, IP-keyed) was repeatedly exhausted by combined traffic, stalling several agents' live role-testing mid-session. Since the limiter is in-memory, this was resolved each time by restarting the backend dev server (clears the limiter instantly) and resuming the affected agent — not a product bug, just cross-agent contention from running the audit at this scale.

## Post-audit fix: login rate-limiter root cause (found via live user report, not an audit agent)

After the audit closed out, a real user reported the login screen intermittently showing "Those credentials don't match any EduNova account" for known-correct credentials. Root cause traced to `server/src/routes/auth.ts`'s `loginLimiter` (`express-rate-limit`, 10/15min): two compounding bugs, not one.

1. **The limiter counted successful logins, not just failures.** `skipSuccessfulRequests` was never set, so 10 correct logins in a row (e.g. a kiosk/demo device cycling through role logins) exhausted the same budget as 10 wrong passwords.
2. **The limiter was keyed by IP address alone, shared across every account.** A real school sits behind one shared office IP/NAT — one person's mistyped password (or a genuine brute-force attempt against one account) locked out every other account on the same network. In dev, several concurrent audit/fix agents plus the real browser session all shared `localhost`'s one bucket.

Fixed both: `skipSuccessfulRequests: true`, and `keyGenerator` changed to `ipKeyGenerator(req.ip) + ':' + email` for the login limiter specifically (per-account-per-IP, not blanket-per-IP) — still stops credential stuffing against one account without collateral-locking everyone else sharing that IP. Also fixed the frontend (`src/pages/Login.tsx`) to distinguish a `429` (shows "Too many login attempts, try again in N minutes") and a `403` (shows the real "account inactive" reason) from an actual `401` ("credentials don't match") — previously every failure path funneled into the same misleading credentials message.

Live-verified: 10 wrong passwords against one account correctly 429s on the 11th attempt; a *different* account from the same IP logs in immediately afterward (200, not blocked); 12 consecutive *correct* logins on the same account all return 200 (none consumed by the old success-counting bug). Full gate re-run clean (frontend tsc/eslint, backend tsc, 189/189 tests).

## Findings reviewed and correctly left as-is (documented limitations, not fixed)

- **`employeeId` global uniqueness vs. per-school generation** (first flagged during Phase 28's own build) — `nextEmployeeId` counts within one school but the column is globally unique across the whole database, so two schools' first same-year hire could theoretically collide. Confirmed still present; deferred as Low severity since it only bites a genuine multi-school deployment, which is rare and not the primary use case today.
- **`loadSampleData()` cannot be safely run against a second school** in the same database — `SEED_TERMS`/`SUBJECTS` use hardcoded, non-school-scoped primary keys (`'t1'`, `'math'`, etc.), so loading sample data into a second school collides with the first school's rows. Confirmed via live reproduction; the failure is a clean transaction rollback (no data corruption), just a blocked workflow. This only affects the Phase 28 multi-school onboarding path in a from-scratch multi-tenant deployment, not any single-school usage — documented here as a known gap rather than fixed, given it's a narrow onboarding-tooling issue rather than a live user-facing defect.
- **No maker-checker control on the Applications approval flow** — a single staff account can both submit and approve the same admission application, unlike the sibling `ParentVerification` flow which explicitly blocks self-verification. This is a product/process decision (internal controls posture), not a security bypass — the actor is already a trusted staff-tier role. Flagged for the product owner's judgment call, not auto-fixed.
- **Non-atomic sequence counters** (`invoiceNo`/`receiptNo`/`slipNo`/`employeeId`, generated via `count()` then `count+1` with no retry-on-conflict) — a real race-condition class across every numbered-document generator in the app, hit once live under heavy concurrent audit-agent load as a 500 on a unique-constraint violation. Low severity for a real school's actual concurrency level (a handful of office staff, not six simultaneous automated agents); a proper fix would touch every numbered-document generator in the codebase uniformly and was judged out of scope for this pass — worth a dedicated future pass if higher concurrency is ever expected.
- **Open house-points ledger read** (`GET /culture/house-points?houseActivityId=`, no role gate — any authenticated student/parent can read the full itemized ledger for any house, including staff member names) — matches the frontend's own "open to everyone, it's a morale feature" design intent; flagged for product confirmation rather than treated as a bug.
- **Seeded sample-data Rooms all ship with `capacity: null`**, silently disabling the exam-seating capacity guard by default until an admin sets a real capacity via the Rooms screen (which works correctly once set). A demo-data completeness gap, not a code defect.
- **`commitAutoGenerate` (Phase 26) can silently no-op a class selected for full-regenerate** if the generator places zero draft entries for that specific class (a fully teacher-constrained scenario) — the class's existing hand-built grid then isn't cleared despite the user confirming the destructive-action warning for it. Narrow edge case, not reproduced live (would require deliberately exhausting every teacher slot for one class); noted for a future pass.
- **`GET /api/discipline/:id`** has no dedicated route (only list/create/patch/status/notes) — dead-code gap, not exploited anywhere in the frontend, which only ever fetches via the list endpoint.

## Bottom line

Six parallel audit agents live-tested every domain across all 30 phases of the ERP. Two Critical bugs (real money-integrity races), two High bugs (a GL double-post and an irreversible data-loss action), and four Medium bugs were found and fixed, each with a regression test where practical and live re-verification against the real running app. A further set of Low-severity/narrow-scope findings were reviewed and consciously left as documented limitations rather than fixed, matching this project's established pattern (e.g. the Phase 28 `employeeId` finding) of flagging real gaps honestly rather than silently patching over judgment calls that belong to a future phase or the product owner.
