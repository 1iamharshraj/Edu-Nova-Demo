# Advanced Timetable Generation — Roadmap

Source: the user's own detailed spec ("School ERP — Advanced Timetable Generation") plus a discussion pass that added: track/stream sectioning nuances (JEE/NEET, skim-then-balance, inconsistent real-world rule enforcement), working-day/Saturday configurability, teacher subject+grade-range qualification, substitution policy modes + minimum notice period, and a strengthened Admissions module as the entry point that feeds all of it. This is a genuinely large build — 12 phases (T0–T11), the biggest single effort in this project's history. Built the same way every prior phase was: detailed spec written just before that phase's agents launch, server+frontend agent pairs, hand-integration, full quality-gate verification, live testing, reset.

## Key architectural decisions (made now, flagged for approval — not silently assumed)

**D1 — DECIDED (user override): no separate runtime. The solver is built and extended entirely in TypeScript, adapted into the existing Node backend/Phase 26 engine — not a Python/OR-Tools microservice.** This changes what T0 is for: instead of a Python-feasibility spike, T0 is now a **research-and-prototype spike to find the strongest pure-TypeScript approach**, evaluated in this order: (1) extend Phase 26's existing backtracking generator with local-search improvement (simulated annealing / tabu search) to handle soft-constraint optimization and a real lexicographic objective hierarchy, since that engine and its conflict-detection integration already exist and work; (2) evaluate whether a pure-JS/WASM ILP/CSP library (e.g. a WASM build of a real MIP solver) is worth pulling in for the hard-constraint-satisfaction core specifically, IF hand-rolled backtracking+local-search proves insufficient at real school scale (hundreds of teachers/sessions) — only reached for if (1) genuinely can't hit acceptable solve times/quality. T0's job is to produce real benchmark numbers (solve time, solution quality vs. a hand-checked reference, infeasibility-detection accuracy) against a realistic problem size before T4/T5 commit to one approach — same rigor as the original Python spike, just aimed at a different target architecture. No new runtime, no new deployment target, no new ops burden — this stays inside the existing stack.

**D2 — `Cohort` layers ON TOP OF the existing `Class` model, not replacing it.** The current schema already has `Board → Grade → Stream → Class` (Class = board+grade+stream+section, unique per board — this is the real "Class 12-A" schools mean colloquially). Rather than a disruptive migration, every `Class` gets an **implicit 1:1 "section cohort"** auto-created (Class 12-A → Cohort "12-A"), so the common case (one section, normal scheduling) needs zero new configuration and nothing breaks. Only schools that actually need cross-section grouping (grade-wide "12-ALL", JEE/NEET, elective baskets) explicitly define additional `Cohort` rows referencing multiple member classes. `TeachingRequirement` always scopes to a `Cohort`, never directly to `Class` — for the common case that cohort just happens to be the auto-generated 1:1 one.

**D3 — `TimetableEntry` (the existing, deeply-embedded model) stays as a real, populated table — a materialized compatibility layer, not replaced.** This app currently reads `TimetableEntry(classId, termId, dayOfWeek, periodIdx)` directly from: Take Attendance, the syllabus pace calculator (Phase 18), teacher-workload analytics (Phase 19), exam-clash detection (Phase 25), hostel roll-call timing, both teacher's and parent's timetable views, and the just-shipped Phase 26 auto-generator — over a dozen call sites across already-shipped, already-tested features. A full cutover would mean touching all of them simultaneously with high regression risk. Instead: every `TimetableSession` (even ones spanning a `SharedSession` across multiple cohorts) writes one real `TimetableEntry` row per underlying `Class` it touches — e.g. a JEE-cohort session spanning base classes 12-A and 12-B at Monday P3 writes two `TimetableEntry` rows (one per class), same teacher/room/period on both. This means the **existing teacher/room conflict-detection engine doesn't even need to change** — it already checks a teacher's busy-ness across every class for a given day/period, which is exactly correct once fed these materialized rows. New capability (versioning, locks, cohorts, shared sessions) lives in the new tables; `TimetableEntry` becomes generated output, not hand-authored, once this system is live for a given school — but every existing consumer keeps working completely unchanged.

**D4 — Admissions is the intake system, expanded to actually capture what downstream needs, INCLUDING full India-specific quota/reservation and physical-document-custody management** — per the user's explicit, emphatic ask ("obviously quite required," "collect all the required certificates," "save where the actual person's certificate is stored... which room and shelf," "when getting TC should be given [back]"). This is now a two-part phase (T2 Part A / Part B, see below) rather than a light data-model addition — it's genuinely one of the largest phases in this roadmap.

**D9 — Testing bar raised for every remaining phase**: per-phase verification must include real frontend exercise (not API-only) AND an explicit UX-fit judgment pass — does the feature actually work well as built, or does it need a popup↔page change (reusing exactly the pattern from the UI-architecture-fix work earlier this session)? A phase isn't "done" on a green test suite alone; it needs a live judgment call on whether the UI serves the feature well, with authority to convert the surface if it doesn't.

**D10 — The manual-override system for a published/generated timetable (T7) is elevated to a first-class, carefully-built capability**, not a light "allow edits" afterthought — per the user's explicit ask for "a proper system around it" once the old simple generator retires. See T7.

**D5 — Track eligibility rules are advisory-by-default with a strict-mode option, override always requires a reason + approver, and overrides are surfaced (not hidden) in an exceptions report** — per the "schools don't always enforce their own rule" discussion.

**D6 — Substitution selection mode is a per-school policy** (`TEACHER_INITIATED | ADMIN_ASSIGNED | HYBRID`), not one fixed flow, with a configurable minimum-notice-period policy governing whether the pre-arranged-substitution workflow is even attempted before falling back to admin emergency assignment. A substitute's acceptance only becomes a real (`LOCKED`) hold once the teacher's leave is actually approved — never before.

**D7 — Working days and period structure are school-level configuration, not hardcoded.** `WorkingDayPattern` (which weekdays teach at all, including alternating-Saturday patterns) plus a `PeriodTemplate` that can vary **by day of week**, not one flat template for the whole week (Saturday half-days, Friday-with-extra-assembly, etc.).

**D8 — Phase T11 (Academic Progress Integration + Term-End Evaluation, the user's own §13/§14) stays explicitly deferred**, exactly as the original spec itself recommended — built only after T0–T10 are live and stable in at least one real school.

## Phase list

### Phase T0 — TypeScript solver research spike — **DONE**

**Result: hand-rolled TS backtracking + simulated annealing is sufficient — build T4/T5 on it, no WASM/Python needed.** Real benchmarks (throwaway spike at `server/scratch/t0-solver-spike/spike.ts`, not wired into the app):
- One-grade scale (6 sections/34 teachers/270 periods-week demand): greedy initial placement is ~1ms; SA at a 5s budget cuts total penalty score 58.8% (lab splits 27→11, teacher idle gaps 32→0) with **zero hard-constraint violations at any point** — 15s/30s budgets barely improve further (~59%), so 5s is the practical sweet spot.
- Whole-school scale (8x, extrapolated by literally running a scaled synthetic problem): greedy stays ~free (11ms); SA throughput fell ~6.7x (11.6k → 1.7k iterations/sec) because the spike's scorer does a naive full-rescore per move — a known, fixable engineering gap, not an algorithmic ceiling. 30s budget still gets a genuinely useful 42% penalty reduction even unoptimized.
- **Two concrete fixes required before T4/T5**: (1) incremental/delta scoring instead of full-rescore-per-move, (2) decompose generation by grade/cohort rather than one monolithic whole-school solve — timetabling is naturally near block-diagonal (different grades rarely share periods/teachers), and T1's `Cohort` model already structurally supports this decomposition.
- Landscape check: `jsLPSolver` (pure-JS MIP) is a poor fit — sized for hundreds of variables, this problem has thousands. `or-tools-wasm` is a real WASM CP-SAT port and the most credible fallback if ever revisited, but solo-maintained, needs a large bundle + worker threads + COOP/COEP headers — directly conflicts with the "no new ops burden" intent behind rejecting Python. Not worth pulling in now.
- From `autogen.ts` (Phase 26, already shipped): reuse the occupancy-map pattern, lab-matching heuristic, and double-period pairing as-is for the new initial-solution stage. Must extend: it's currently Mon–Fri hardcoded (no Saturday/day-of-week variation) and has zero soft-constraint scoring or refinement — T4/T5 add the entire scoring/SA layer fresh. Architecture note for T4/T5: refinement should run per-cohort-group (per D2), not as one school-wide pass, both for the performance reason above and because it's the structurally correct scope.

### Phase T2 — Strong Admissions (two parts — this is now one of the largest phases in the roadmap)

**Part A — Admission data expansion.** Extend `Application` well beyond today's bare `targetClassId` pointer, organized into what's actually consumed downstream (not a kitchen-sink form):
- **Prior academics**: previous school/board, last grade completed, structured subject-wise marks (individual key-subject scores, not just an aggregate — needed for track-eligibility checks in T3), marksheet document upload.
- **Track/stream preference** (for 11th-entry applicants): declared preference + the eligibility check itself runs at approval time using T3's `TrackEligibilityRule` in ADVISORY or STRICT mode per the school's own simple toggle (D5) — admission and internal promotion share one eligibility mechanism, not two.
- **Sibling linkage**: link to an existing student's enrollment (siblings are already derivable via shared `Guardian` — verify this is queryable as-is before adding a redundant field) — feeds the Sectioning Engine's "siblings together" validation option.
- **Category/quota — real, structured, India-specific** (see Part B for the certificate/document side of this): a configurable `AdmissionCategory` (General / SC / ST / OBC / EWS / RTE / Management / Staff-Ward / Sports-Talent / Minority / Defense/Ex-servicemen, etc. — school-editable list, not a hardcoded enum, since reservation categories and their exact names vary by state and school type). Connects to Phase 5's existing Scholarship/concession system as an optional downstream link (e.g. an RTE-quota admission surfaces as an eligible-for-fee-waiver-review candidate), not a forced coupling.
- **Health/medical flags captured at intake**, handed off to pre-populate Phase 8's existing `HealthRecord` on enrollment (capture once, hand off once — don't duplicate HealthRecord's job).
- **Transport requirement** (route/stop need) captured at intake, handed to Phase 12's Transport module post-enrollment.
- Approval flow otherwise unchanged (still creates student+parent+enrollment+guardian atomically) — this phase is a strict superset of what exists.

**Part B — Document & certificate management, including physical custody tracking.** This is the deep, India-specific piece the user explicitly asked for.

- **`RequiredDocumentType`** — a school-configurable catalog (not hardcoded), seeded with a real default set covering standard Indian school admission requirements: Birth Certificate, previous-school Transfer Certificate (TC), previous-school report cards/mark sheets, Migration Certificate (board/state change), Character Certificate, Aadhaar card copy (student, sometimes parents), passport photographs, address proof, Caste Certificate (SC/ST/OBC/EWS — issued by a competent government authority), Income Certificate (EWS/RTE eligibility), Domicile/Residence Certificate (RTE neighborhood-criterion, state quota), Disability Certificate (disability quota/accommodations), Minority Certificate (minority-institution quota where applicable), RTE Allotment Letter (if admitted via government RTE lottery), Medical/Immunization/Fitness Certificate, Bank Passbook copy (RTE reimbursement / scholarship disbursement tracking in some states), Sports/Extracurricular Achievement Certificates (talent quota), parent ID/employment proof (staff-ward or employer-tie-up quota), previous school's Fee Clearance/No-Dues Certificate, and relevant declarations/undertakings. Each type carries a **condition** for when it's required (e.g. Caste Certificate required IF `category IN (SC,ST,OBC,EWS)`; RTE Allotment Letter required IF `admissionMode = RTE`; Migration Certificate required IF `previousBoard != currentBoard`) — conditional, not a flat checklist everyone fills identically.
- **`SubmittedDocument`** — links to the existing `File` upload system for a digital scan (reuse what's already built, don't duplicate it) PLUS the physical-custody fields the user specifically asked for: `physicalLocation` (room/records-area, cabinet or shelf identifier, folder/file reference — a simple structured location, not the same `Room` entity used for classrooms/labs, since a records room isn't a teaching space), `isOriginal` (bool — an original needs custody tracking; a photocopy doesn't), `receivedDate`, `status` (HELD | RETURNED | LOST | NOT_APPLICABLE), `returnedDate`, `returnedTo`, `returnReason`.
- **Admission completeness checklist**: the Application view shows exactly which required documents (per the category-conditional rules above) are collected vs. missing — configurable whether missing documents hard-block approval or are soft-required (collectable within N days post-admission).
- **TC-issuance document-return workflow** (the piece the user explicitly flagged — "when getting TC should be given [back] and stuffs"): extends the existing Phase 4 Certificate/TC issuance flow so that issuing a TC surfaces a checklist of every document on file for that student marked `isOriginal=true, status=HELD`, and issuance requires either marking each as `RETURNED` (with who it was returned to) or an explicit acknowledged exception — closing the real, common failure mode of schools losing track of original certificates at withdrawal time.
- A simple physical-records report ("which documents are currently held, where, for which students") for school office/records staff — genuinely useful operational output, not just compliance theater.

### Phase T5 — Full assignment modes + soft constraints — **DONE**
282/282 backend tests (258 + 24 new). ### Phase T9 — Substitution workflow — **DONE**
339/339 backend tests (313 + 26 new). `LeaveRequest` genuinely extended in place (not forked): `PENDING_SUBSTITUTION` sits in its lifecycle between `Pending` and `Approved`/`Declined`, and the existing Phase 6 non-teaching leave flow was proven completely unaffected — live-verified a staff leave with no teaching periods stays plain `Pending`→`Approved` with no `substitution` field on the response.
