# Phase 29 — India Compliance & Offline Resilience

Two genuinely unrelated items bundled for scheduling convenience — independent of each other and of every other phase, can run in parallel with Phase 30. Split as two separate agent pairs (4 agents total for this phase: UDISE+ server, UDISE+ frontend, Offline-attendance server, Offline-attendance frontend) rather than forcing one pair to do both, since they touch completely different parts of the stack (a data-export module vs. a frontend service-worker/sync layer).

## Part A — UDISE+ data export

**Honesty constraint, non-negotiable**: nobody on this project has verified the exact current UDISE+ (Unified District Information System for Education Plus, India's school data collection system) form field list against the live government portal, and it changes periodically. Do NOT hardcode a guessed field mapping as if it were verified fact. Instead:

- Build a versioned, documented field-mapping config file: `server/src/modules/compliance/udisePlus.mapping.ts` — export a typed `UDISE_FIELD_MAP` object (version-tagged, e.g. `UDISE_MAPPING_VERSION = '2024-25-draft'`) mapping UDISE+ form sections (School Profile, Enrollment by grade/gender/category, Teacher details, Facilities) to this codebase's actual Prisma fields, based on the well-known PUBLIC STRUCTURE of UDISE+ (grade-wise enrollment counts, teacher qualification/training counts, basic facility checklists — this general shape is well-documented and stable even if exact field codes drift) — and clearly comment every section with `// VERIFY against current UDISE+ portal before real submission — field codes/exact labels may have changed`.
- `GET /api/compliance/udise-export?academicYearId=` (admin/superadmin) — generates the export using the mapping file: real counts from real data (`Enrollment` by grade+gender+category if that field exists on `Student`/`Guardian` — check first, don't invent a category field if none exists, note the gap instead of faking it; `User` role=teacher counts with qualification data from `EmploymentHistory`/employee records; `Room`/facility counts from the `Room` model). Output as a downloadable CSV/JSON matching the mapping file's structure, plus a human-readable summary screen so an admin can sanity-check numbers before manual entry into the actual government portal (this is realistically an assistive export, not a direct government API integration — there is no public UDISE+ submission API to integrate with even if there were credentials).
- Frontend: an admin/superadmin "UDISE+ Export" screen — pick academic year, preview the mapped data with the mapping version clearly displayed, download.
- **In the final report, explicitly restate**: this export accelerates manual UDISE+ form-filling using real school data, it does not submit to any government system, and the field mapping should be verified against the live portal before actual government submission — this must also appear as an on-screen note in the UI itself, not just in the code comment, so a real school admin isn't misled about what "export" means here.

## Part B — Offline-first attendance marking

This is real frontend engineering (service worker + local persistence + background sync), not a small add-on — treat it with the same care as any other substantial frontend phase.

- **Scope**: only the single highest-value, most bounded workflow — marking daily class attendance (`AttendanceSession`/`AttendanceRecord`, the existing teacher "take attendance" screen) — works offline. Do not attempt to make the entire app offline-capable; that's a different, much larger project.
- Service worker (Vite PWA plugin if the project doesn't already have one — check `vite.config.ts`/`package.json` first for existing PWA/service-worker tooling before adding a new dependency; `vite-plugin-pwa` is the standard choice if none exists) caches the attendance-marking screen's static assets and the specific data it needs (the class roster for sessions the teacher has recently opened, or explicitly pre-fetched) so the screen itself loads with no network.
- Local queue: when `POST`ing attendance while offline (detect via `navigator.onLine` plus an actual failed-fetch fallback, since `navigator.onLine` alone is unreliable), write the pending submission to IndexedDB (a small dedicated store, not `localStorage` — attendance payloads plus retry metadata deserve a real structured store) instead of failing. Show the teacher a clear "saved offline, will sync when connected" state per session — never a silent failure, never a false "submitted" success that hasn't actually reached the server yet.
- Background sync: when connectivity returns (the `online` event, plus the service worker's Background Sync API where supported, with a foreground retry-on-focus fallback for browsers without Background Sync support — Safari notably lacks it, so don't rely on it exclusively), replay queued submissions against the real `POST` attendance endpoint in order, handle the case where a session's data has since changed server-side (e.g. another teacher already submitted it) with a clear conflict message rather than silently overwriting, and clearly surface sync completion/failure to the teacher (a small persistent indicator, not just a toast that can be missed).
- **Idempotency**: the existing attendance-submission endpoint must be safe to retry (check if it already is — Phase 5's attendance work may already be idempotent per-session; if not, this phase needs to add a client-generated idempotency key so a queued-then-retried submission during a flaky connection doesn't double-submit).
- Frontend: the existing "Take Attendance" screen (find it — likely `src/portal/modules/attendance.tsx` or similar) gets the offline-queue UI treatment described above; no new standalone module needed, this is an enhancement to that existing screen's resilience.

## Ground rules
Same as every previous phase: Part A — no new Prisma models, `server/src/modules/compliance/{router,service,schema}.ts` (or extend an existing module if a compliance-adjacent one already exists — check first), zod validation, `requireRole()` (admin/superadmin), `HttpError`, `audit()` on export generation, no cleanup block needed (no new tables). Part B — no backend changes beyond confirming/adding idempotency to the existing attendance endpoint, real service-worker code (not a stub), IndexedDB via a real small wrapper (a minimal hand-rolled one is fine, or `idb` from npm if it keeps things cleaner — don't hand-roll a large abstraction for this). Both parts: no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent (Part A needs a new nav entry; Part B does not, it's an enhancement to an existing screen), full tsc/eslint/87-test verification, live verification — Part A: generate a real UDISE+ export against real seeded enrollment/staff data and confirm the numbers are correct by cross-checking against the actual database counts; Part B: this needs genuine manual/scripted verification of the offline flow (e.g. a Playwright test that goes offline via CDP network throttling, marks attendance, confirms it queues, goes back online, confirms it syncs and appears server-side) — don't just claim it works, actually exercise the offline→online cycle and show the trace in the report.
