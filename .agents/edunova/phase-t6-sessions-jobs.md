# Phase T6 — Sessions, Generation Jobs, Diagnostics

Sixth phase of the Advanced Timetable Generation project (`advanced-timetable-roadmap.md` — read in full, especially D3, T0's results). Read T4/T5's shipped code THOROUGHLY first (`server/src/modules/timetable/{autogen.ts,solver.ts,teachingRequirements.ts,constraints.ts}` plus T5's refinement/preference files) — this phase wraps the working solver core (T4+T5) in the proper session/job/diagnostics model the original spec described, and is where D3's "materialize into real `TimetableEntry`" compatibility layer gets formalized as a first-class concept rather than an implicit side effect of `commit`.

## 1. TimetableSession / SharedSession / ElectiveBlock

- `TimetableSession { id, schoolId, teachingAssignmentId, sessionType (SINGLE|DOUBLE|TRIPLE|LAB_BLOCK|ASSEMBLY|LUNCH|ACTIVITY|STUDY|FREE|SHARED|FIXED), durationPeriods, isSplittable, timetableVersionId }` + `TimetableSessionEntry { sessionId, dayOfWeek, periodIdx }` (one row per period a session occupies — the "shaped" output of a teaching requirement's `requiredPeriodsPerWeek`).
- `SessionCohort { sessionId, cohortId }` — a session with 2+ rows here is a genuine SharedSession: it satisfies the requirement of EVERY linked cohort for that slot and blocks that period in each linked cohort, never treated as a collision between them. This is the concept the original spec's "12-A + 12-B combined English" example describes — implement it exactly that way, don't approximate with two independent sessions that happen to share a slot (that would re-introduce the collision-detection false-positive the original spec explicitly warns about).
- **`ElectiveBlock { id, schoolId, gradeId, name, dayOfWeek, periodIdx, durationPeriods }`** (our discussion's addition, beyond the original spec's SharedSession alone): a grade-wide reserved slot where multiple parallel elective offerings run simultaneously so students can choose between them without a schedule clash — model as one `ElectiveBlock` referencing N `TeachingRequirement`s (one per elective subject offered in that slot), each requirement's resulting session locked to the block's exact day/period. This is NOT the same as SharedSession (which merges cohorts into one session) — it's the inverse: one slot, multiple parallel sessions, students individually bucketed by their elective choice (reuse T3's Activity/registration pattern for capturing which student picked which elective, if that data doesn't already exist elsewhere).

## 2. Materialization into TimetableEntry (D3, formalized)

- Every `TimetableSessionEntry` writes exactly one real `TimetableEntry` row per underlying `Class` its linked cohort(s) touch (a SharedSession spanning 2 base classes writes 2 `TimetableEntry` rows, same teacher/room/period, one per class — confirmed by T0/T4's own findings that this needs zero changes to the existing conflict-detection engine, which already checks a teacher's busy-ness across every class for a slot). This materialization step is what `commit` (already built in T4) actually does — this phase just makes the `TimetableSession` layer the real source of truth `commit` reads from, rather than `commit` working directly off `draftEntries` as it does today. Read T4's `commit` implementation carefully before changing it — preserve its exact validation/audit behavior, just change what it reads from.

## 3. TimetableGenerationJob (first-class object)

- `TimetableGenerationJob { id, schoolId, academicYearId, termId, scopeCohortIds[], status (QUEUED|BUILDING_MODEL|SOLVING|VALIDATING|COMPLETED|FAILED|CANCELLED), progress, currentStage, startedAt, completedAt, solverVersion, timeLimit, inputSnapshot (json), constraintSnapshot (json — the active Constraint rows at generation time), preferenceSnapshot (json — the active Preference/PreferenceProfile at generation time), randomSeed, solverParameters, resultVersionId, errorCode, errorDetails }`.
- Wrap T4/T5's existing generate→refine pipeline in this job model — for the realistic problem sizes T0 benchmarked (single-grade generation completing in low single-digit seconds), a synchronous request/response is fine; for whole-school scale (T0 found SA refinement genuinely slow there without the decomposition fix — confirm T5 actually applied that fix and re-benchmark at whole-school scale here), the job should be genuinely async (check whether this codebase has any existing background-job/worker infrastructure to reuse — search for one before building a new queueing mechanism from scratch) with the frontend polling job status.
- **Reproducibility**: every field above must actually be enough to regenerate byte-identical output months later given the same inputs — test this explicitly, don't just claim it.

## 4. Infeasibility diagnostics (real, not "generation failed")

- When generation can't produce a feasible result for some/all of a scope, compute a structured diagnosis, not a dead end: for each unsatisfiable `TeachingRequirement`, identify the specific conflicting constraints (e.g. "Grade 12-A requires 42 sessions/week, available periods: 35" or "Physics Lab has only 4 compatible periods available") and suggest concrete actions (reduce periods/week, allow Saturday, relax a specific teacher's availability) — computed deterministically from the actual constraint model (which slots were tried and why each failed), never free-text guesswork or an LLM call.

## Ground rules
Same rigor as every phase: additive migrations, extend `server/src/modules/timetable/`, zod validation, `requireRole()`, `HttpError`, `audit()`, reset-cleanup blocks, full `tsc`/`npm test` gate clean, no git commands, no `/admin/reset`/`/admin/load-sample-data` except a final verification step.

**Critical regression requirement**: T4/T5's existing generate/commit endpoints and Phase 26's original UI must keep working throughout.

**Live verification required**: generate a real SharedSession (two cohorts merged for one class) and confirm the existing conflict-detection engine correctly treats it as non-colliding while still catching a genuine double-booking elsewhere; generate a real ElectiveBlock with 2+ parallel elective offerings and confirm students can be scheduled into either without a clash; deliberately construct an infeasible scenario (e.g. a grade needing more periods/week than exist) and confirm the diagnostic output names the real conflicting numbers and offers sensible suggested actions rather than a bare failure; regenerate the exact same job twice with the same snapshot and confirm byte-identical output (reproducibility, actually tested).

**Testing bar** (per roadmap D9): live UI verification for the job-progress display and the infeasibility-diagnostic screen specifically — a bare "failed" error here would be a real regression in trust, this needs to render legibly.
