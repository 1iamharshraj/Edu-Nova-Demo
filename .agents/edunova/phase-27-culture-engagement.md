# Phase 27 — Culture & Engagement

Extends the existing Activities module (`server/src/modules/activities/`) and Achievement model (`Achievement`, used by report cards/student reports). Independent of everything else — can run in parallel with Phase 25.

Read `server/src/modules/activities/service.ts` and `server/prisma/schema.prisma`'s `Achievement` model first. Confirmed by code read: "house" is currently just one `Activity.kind` value (`house`) with registration semantics (join a house) — there is no points/leaderboard concept anywhere yet. This phase adds one.

## 1. Inter-house points leaderboard

- `HousePoints { id, schoolId, houseActivityId (the Activity row with kind='house' a student belongs to — resolve "which house is a student in" via their Registered ActivityRegistration for that house, don't add a redundant houseId field to User/Enrollment), points, reason, awardedById, awardedAt, sourceType? (Sports|Academic|Discipline|Event|Manual), sourceRefId? }` — staff/admin award points to a house (not an individual student) for something: a sports win, a competition, general good conduct. Simple additive ledger, not a replace-the-total model — the leaderboard is a SUM query, not a stored running total (avoids race conditions, matches how the GL/library-fine patterns already do it elsewhere in this codebase).
- `POST /api/culture/house-points` (staff/admin) — award points to a house.
- `GET /api/culture/house-points/leaderboard?termId=` — every house (derived from distinct `Activity` rows where `kind='house'`) with its summed points, ranked. `GET /api/culture/house-points?houseActivityId=` — the itemized ledger for one house (transparency — a house captain/student should be able to see WHY the score is what it is, not just the number).
- **Feed integration**: reuse the existing Feed/notifications infrastructure (`server/src/modules/feed/`) — when points are awarded, post a feed item (following whatever pattern existing feed posts use, e.g. announcements) so the award is visible school-wide, not just on a dedicated leaderboard screen buried in navigation. Check the feed module first for the right way to create a system-generated post vs. a user-authored one.
- Frontend: a leaderboard screen (bar chart or ranked list, live standings) visible to everyone (students/parents/staff/admin — this is a morale feature, keep it open), an award-points form (staff/admin), and the feed-post integration should just work once the backend posts to feed — verify it renders correctly in the existing Feed UI.

## 2. Student digital portfolio

- **No new model** — this is a presentational aggregation of data that already exists: `Achievement` rows (already has `title`, `detail`, `date`, `category`, `verifiedById`/`verifiedAt`, `fileIds`), plus certificates issued to the student (`Certificate` model, check `server/src/modules/certificates/`), plus `ActivityRegistration` history (clubs/houses/events/excursions joined over the years), plus co-curricular marks if `Assessment`/reports track anything non-academic — check before assuming that last one exists; if not, skip it, don't invent a new field.
- `GET /api/culture/portfolio/:studentId` (self/guardian, class teacher, staff, admin) — one aggregated payload: verified achievements grouped by category, certificates list (with download links reusing the existing certificate PDF endpoint), activity/club/house history across academic years, sorted newest-first, with a simple summary count block (X achievements, Y certificates, Z activities across N years).
- `GET /api/culture/portfolio/:studentId/export` — a single combined PDF (reuse `server/src/lib/pdf.ts` patterns) suitable for the student to actually use (e.g. attached to a scholarship/college application) — a clean "Student Portfolio" document, not just a dump of the JSON.
- **Alumni connection**: if the student has since become an alumnus (check the Alumni module, Phase 12, for how it links a `User`/former student record), the portfolio endpoint should still resolve and work identically post-graduation — verify this explicitly, since it's the actual point of the "connects to Alumni module" line in the roadmap (a portfolio that stops working the day someone graduates defeats the purpose).
- Frontend: a "My Portfolio" screen (student, and guardian viewing a ward), a staff/admin-facing "View Portfolio" access point from the student profile/report screen, and a "Download Portfolio PDF" button.

## Ground rules
Same as every previous phase: additive migration for `HousePoints` only (item 2 is read-only aggregation, no new tables), `server/src/modules/culture/{router,service,schema}.ts`, zod validation, `requireRole()`/scope helpers (self-or-guardian pattern already used elsewhere for portfolio access), `HttpError`, `audit()` on point-award mutations, add a Phase 27 cleanup block to `POST /reset` for `HousePoints`, no git commands, no `/admin/reset`/`/admin/load-sample-data` except your own final step, server/frontend split with Portal.tsx changes described-not-made by the frontend agent, full tsc/eslint/87-test verification, live curl+UI verification — specifically award points to two different houses and confirm the leaderboard ranks them correctly and a feed post appears, and generate a real portfolio PDF for a seeded student with at least one verified achievement and one certificate.
