# Phase T1 — Scheduling Data-Model Foundations

First real-schema phase of the Advanced Timetable Generation project (`advanced-timetable-roadmap.md` — read that in full first, especially decisions D1-D10). Purely additive data model + a small amount of admin UI to configure it. No solver, no generation logic yet — this phase just gives T3-T9 the vocabulary they need. Read `server/prisma/schema.prisma`'s existing `Class`, `Room`, `Teacher`(=`User` role=teacher), `PeriodTemplate`, `TimetableEntry` models thoroughly before writing anything — every addition here must sit correctly alongside what already exists, not duplicate or conflict with it.

## 1. Cohort (per roadmap decision D2 — layered on top of Class, not replacing it)

- `Cohort { id, schoolId, name, gradeId, sectionClassIds (join table CohortClass, not an array — a cohort can span multiple Class rows), type (SECTION|GRADE|CROSS_SECTION|TRACK|ELECTIVE), autoGenerated (bool), academicYearId }`.
- **Auto-generation**: whenever a `Class` is created (existing flow, Phase 1/1b), auto-create a 1:1 `Cohort` (`type=SECTION`, `autoGenerated=true`) pointing at just that one class. This must happen transparently — existing schools with existing classes get this backfilled by a one-time migration script; new classes get it going forward via the existing class-creation service function (extend it, don't fork a parallel path).
- **Manual cohorts**: admin UI to define additional cohorts referencing 2+ existing classes (e.g. "12-ALL" = every 12th class, "12-JEE" = specific sections' JEE-track subset once T3 exists — T1 just needs the cohort machinery, T3 wires sectioning into it). A cohort's member classes must all share the same `academicYearId` (reject otherwise) — don't allow a cohort to span two years.
- Every later phase (`TeachingRequirement`, `TimetableSession`) references `Cohort`, never `Class` directly, per D2.

## 2. RoomCapability (normalized, per roadmap decision — matches this codebase's junction-table convention, not JSON blobs)

- `Capability { id, schoolId, name, code }` — a small admin-managed catalog (Physics, Chemistry, Biology, Computer, Projector, SmartBoard, ... — seed a sensible default set, school can add more).
- `RoomCapability { roomId, capabilityId }` — join table.
- Extend the existing `Room` admin screen with a capability multi-select. Existing `Room.type` field stays as-is (classroom/lab/ground/etc.) — capabilities are additive detail on top, not a replacement.

## 3. TeacherQualification (replaces the flat qualifications concept for scheduling purposes)

- `TeacherQualification { id, schoolId, teacherId, subjectId, gradeRangeMin, gradeRangeMax (grade level numbers — use the existing `Grade.level` field), proficiency (PRIMARY|SECONDARY), isPrimarySubject }`.
- Check first whether `Teacher`/`User` already has any subject-qualification concept (the existing `ClassSubject.teacherId` assignment implies capability but isn't a declared qualification) — if there's an existing informal signal, this table supersedes it for scheduling purposes without deleting whatever's there today (existing `ClassSubject` assignments keep working unchanged).
- Admin UI: a per-teacher qualifications editor (subject + grade range + proficiency), reachable from the existing teacher profile/People screens.

## 4. Teacher band affinity (declared + verified, per original spec §3)

- Additive fields on `User` (teacher role only, but keep on the shared `User` table per this codebase's existing convention of role-conditional fields): `declaredBandAffinity` (JSON: `{support: STRONG|MEDIUM|NONE, mid: ..., advanced: ...}`), `verifiedBandAffinity` (same shape, nullable — populated only by the future T11 evaluation engine, empty until then), `affinitySource` (DECLARED|VERIFIED, defaults DECLARED).
- Simple self-service UI: a teacher can declare their own band affinity (e.g. in their Profile screen) — three dropdowns. No verified-affinity UI yet (T11's job).

## 5. WorkingDayPattern + per-day PeriodTemplate (per roadmap decision D7)

- Read the existing `PeriodTemplate` model exactly first (it currently defines one flat slot list for the whole week per school/campus/grade-range). Extend it to be **scoped per day-of-week**: either add a `dayOfWeek` field to `PeriodTemplate` itself (a school can then define a different template for Saturday than Mon-Fri) or introduce `PeriodTemplate → PeriodTemplateDay → slots` — read the existing model's exact shape first and choose whichever extension is the smaller, cleaner diff; document which you chose and why.
- `WorkingDayPattern { id, schoolId, academicYearId, workingDays: string[] (subset of Mon-Sun), saturdayPattern (NONE|ALL|ALTERNATE_1_3|ALTERNATE_2_4|HALF_DAY_ALL — cover the common real patterns; keep it an enum with a documented meaning per value, not free text) }`.
- Existing schools default to the current implicit behavior (Mon-Fri, confirmed via Phase 26's own build notes that Saturday was schema-legal but unused) — this phase must not change any existing school's actual generated/displayed timetable unless they explicitly configure something different.
- Admin settings UI: a simple working-days configuration screen (which weekdays teach, Saturday pattern, and the day-scoped period template editor).

## Ground rules
Same rigor as every other phase in this project: additive migrations only, zod validation, `requireRole()`, `HttpError`, `audit()` on mutations, add reset-cleanup blocks for every new table to `POST /reset`, no git commands, no `/admin/reset`/`/admin/load-sample-data` except a final verification step, server/frontend split with clear ownership, full `tsc`/`eslint`/`npm test` gate clean, live verification against the real running app — specifically confirm: creating a new Class still auto-creates its 1:1 Cohort, an existing school's timetable/period display is byte-identical before and after this phase (regression check, this phase must be invisible to a school that doesn't touch the new config screens), and a manually-created cross-section Cohort correctly rejects mixing classes from two different academic years.

**Testing bar** (per roadmap D9): live UI verification is required, not just API calls — actually open the new admin screens (capability editor, teacher qualifications, working-days config) in a real browser and confirm they're usable, not just that the endpoints return 200.
