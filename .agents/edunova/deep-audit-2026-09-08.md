# EduNova — Deep Audit (2026-09-08)

> **Update 2026-09-08, later same day: all Critical and High items below are FIXED and verified.** See the "Fix status" note at the top of each item. Medium items 13 and 14 are also fixed. Remaining open: item 16 (Admin Management redundancy — a product decision, not a bug) and item 17 (parent verification document-upload path — needs a dedicated live-test pass, still unconfirmed either way). Low/polish items are untouched.

Six parallel agents live-tested every screen in the app (Playwright, real browser sessions, real CRUD round-trips) and cross-checked every finding against the actual source/API — not a code-read-only pass. This document compiles all findings, ranked by severity, followed by the full per-domain detail.

**Headline**: the backend is overwhelmingly real and well-built — every domain audit independently confirmed genuine Postgres-backed data, correct math (fees/payroll/grades/ranks), idempotent write endpoints, real PDFs, and server-side RBAC that actually rejects unauthorized calls (not just UI-hidden). The problems found are concentrated in two shapes: **(a) a handful of serious backend/security bugs**, and **(b) a systemic "wiring" problem** — features that are fully built and working on the backend but are unreachable or broken because of nav-registry mismatches, wrong notification links, or a frontend crash.

## CRITICAL — fix first

| # | Issue | Where | Impact | Fix status |

| 2 | **Predictable, non-expiring passwords** for accounts created via People & Roles or Admin Management — every account of a role gets the same password (`staff123`, `teacher123`, etc.) and `mustChangePassword` is left `false`. | `server/src/userDefaults.ts` (`rolePassword()`), used by `POST /users` | Any staff member's password is guessable from their role. ## New follow-ups surfaced while fixing item #3

The agent that fixed the authorization bypass (item 3) found two narrower, related gaps while working — neither is a regression, both pre-date this fix, and both are lower-risk than item 3 itself, so they were deliberately left for a dedicated follow-up rather than folded into this pass:

- **Read-side mark/submission visibility is still coarse-grained**: a teacher who shares *any* subject in a class can still see all students' marks/submissions for subjects they don't teach in that class (the write-side bypass is fixed; the analogous read-side imprecision in `assessments`/`homework` `list()` was not, since a `classId`-only query can span multiple subjects and tightening it needs a larger `serializeAssessment`/`serializeHomework` rework).
- **No substitute-teacher carve-out in attendance authorization**: a `Substitution` covering someone else's period doesn't grant the substitute attendance-write access unless they separately hold a `ClassSubject` or are the class teacher. This mirrors pre-existing behavior (not a regression from this fix), but is worth a deliberate design decision.

## What's genuinely solid (no action needed)

- **Academic Setup** (Years/Terms, Boards/Grades, Curriculum, Classes, Rooms, Periods): fully real CRUD, correct cascade logic (curriculum → class subjects), zero RBAC leaks.
- **Fees management, end to end**: fee head → structure → invoice generation (proven idempotent) → parent payment via sandbox gateway → invoice clears → student drops off defaulters list — verified live, exactly as designed.
- **Payroll management, end to end**: real monthly runs (idempotent), correct basic+allowance−deduction math, real downloadable payslip PDFs.
- **Admissions & Certificates, Board Registration, Verifications**: real enrollment creation, real random passwords + forced change (the *correct* reference implementation other account-creation paths should copy), real serial-numbered PDFs, genuine per-student workflow states.
- **Attendance → Gradebook → Rank List → Student Report pipeline**: mathematically consistent across every role's view of the same data (down to the digit).
- **Messaging (where reachable), Meetings, Event Highlights, Discipline, Activity registration/waitlist**: all genuinely real, no leftover fake/simulated behavior (the old "AI parent call" concept and hardcoded highlight placeholder are both fully gone).
- **Server-side RBAC**: every direct-API boundary probe across every domain returned the correct 401/403 — the authorization model itself is sound (bug #3 above is a scoping precision issue within one check, not a missing-check issue).
- **Dark mode, visual/IA consistency**: applied with real discipline across all 6 roles; the app does not feel like disconnected screens built by different people.
